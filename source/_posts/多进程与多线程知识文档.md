## 多进程与多线程对比

### 资源模型

进程拥有独立的地址空间、内存、堆和文件句柄，彼此隔离。一个进程崩溃通常不会影响其他进程，代价是进程间必须借助 IPC 交换数据。

同一进程内的线程共享内存、全局变量和文件句柄，各自只私有栈、寄存器与局部变量。线程通信可以直接读写共享变量，但必须加锁防止竞态。线程内出现未捕获异常或触发致命信号时，可能导致整个进程终止。

### 切换与创建开销

进程切换要更换页表、刷新 TLB、保存整套上下文，开销较大；线程切换只保存少量寄存器，地址空间不变，速度更快。

新建进程需要操作系统分配一整套内存资源，开销高；新建线程只是在已有进程里增加一条执行流，开销低。

### 并发能力与 GIL

设 CPU 核心数为 N。多进程不受 GIL 限制，N 个进程可以同时跑在 N 个核上，实现真正并行。

CPython 的多线程受 GIL 约束，同一时刻一个进程内只有一个线程执行 Python 字节码，CPU 密集型任务用多线程几乎无法提速。IO 密集型任务在等待网络、磁盘或 sleep 时线程会释放 GIL，因此多线程依然有效。

### 生命周期

进程之间存在父子关系，资源独立，子进程退出后需要父进程回收，否则可能形成僵尸进程。线程依附于进程，主线程退出即整个进程结束，通常用 join 等待子线程完成。

### 协程

协程是用户态的调度单位，比线程更轻，不需要操作系统参与调度，在单线程内部由程序自身切换，几乎无切换开销，适合超高并发 IO 场景，典型实现是 asyncio。协程运行在单线程内，本身不涉及 GIL 切换。

## GIL 全局解释器锁

### 定义与作用域

GIL，全称 Global Interpreter Lock，是 CPython 的一把进程级互斥锁。每个 Python 进程有且只有一把自己的 GIL，线程必须先拿到它才能执行 Python 字节码。

它不是 Python 语言的特性，而是 CPython 这一主流解释器的实现选择。Jython、IronPython 等实现并不采用这种设计，PyPy 标准版仍然保留 GIL。

同一进程开两个线程跑 CPU 计算时，两个线程轮流抢锁、交替执行字节码，任意时刻只有一个线程在跑。结果是单进程多线程只能并发，不能利用多核做 CPU 并行。

### 释放时机

线程在以下阻塞点会主动释放 GIL，让其他线程继续运行：

- sleep
- 网络请求与 socket 等待响应
- 文件与磁盘 IO
- input 等待输入

另一类释放来自解释器的强制切换。CPython 3.2 之前按已执行的字节码条数触发切换，之后改为基于时间的切换间隔，默认约 5 毫秒，可通过 sys.getswitchinterval 查看与调整。

主动释放是 IO 密集场景多线程仍然有效的原因：线程卡在等待时把 GIL 交出去，CPU 不会空转。

### 对并发的影响

CPU 密集任务在单进程多线程下无法多核并行，提速很差；改用 multiprocessing 后，每个进程拥有独立 GIL，可以分布到多个核上并行执行。

IO 密集任务基本不受 GIL 拖累。

GIL 保护的是字节码执行，不保护业务数据。一条 Python 语句往往对应多条字节码，中途仍可能切换线程，因此共享变量的修改必须自行使用 threading.Lock 或 multiprocessing.Lock。

### 设计动因

CPython 使用引用计数做内存管理，GIL 让引用计数的增减天然原子化，简化了 C 扩展的内存管理，扩展作者不必自己加锁。早期计算机以单核为主，这一实现简单、开发成本低。

彻底移除 GIL 的阻力来自生态：大量现存 C 扩展依赖 GIL 提供的隐式保护，直接移除会让它们失效或产生并发错误。

## 解释器实现与 GIL

### python解释器对比

| 解释器 | GIL | 多线程多核并行 | Python 生态 |
| --- | --- | --- | --- |
| CPython | 有 | 不可以 | 最完整 |
| PyPy 标准版 | 有 | 不可以 | 较好，部分 C 扩展不兼容 |
| Jython | 无 | 可以 | 极弱，停留在 Python 2.7 |
| IronPython | 无 | 可以 | 极弱 |
| GraalPy | 不沿用 CPython 式 GIL | 可以 | 中等，仍不及 CPython |
| PyPy-STM | 无 | 可以 | 实验项目，已停止维护 |

- Jython 运行在 JVM 上，复用 Java 线程模型，可无缝调用 Java 库，但最高只支持 Python 2.7，numpy、pandas 等 C 扩展基本无法使用，生产环境已很少见。
- IronPython 运行在 .NET CLR 上，复用 C# 线程机制，与 .NET 生态互通，同样对 CPython 的 C 扩展支持很差。
- PyPy 带 JIT，纯 Python 代码的单线程性能显著强于 CPython，但标准版仍有 GIL。PyPy-STM 曾以软件事务内存实现无 GIL 并行，项目早已停滞，不适合生产。
- GraalPy 是 GraalVM 上的 Python 实现，不沿用 CPython 的 GIL 设计，配合 JIT 支持多线程并行，生态好于 Jython 与 IronPython，但仍弱于 CPython。

### 无 GIL 方案的生态代价

无 GIL 解释器最大的短板是难以运行基于 CPython C API 的扩展库。numpy、pandas、scipy、torch、opencv 底层都由 C 编写并针对 CPython 开发，Jython 与 IronPython 几乎跑不动它们。重度依赖科学计算与 AI 库的项目，换解释器这条路基本走不通。

### CPython 的无 GIL 演进

官方通过 PEP 703 推进可关闭 GIL 的 CPython 构建，也叫 Free-Threaded CPython，好处是不必更换解释器即可沿用 CPython 生态。目前仍属实验性选项：若导入尚未适配的 C 扩展，解释器会重新启用 GIL，行为退回原有模式。

## JIT 即时编译

### 三种执行模式

JIT，即 Just-In-Time 即时编译，指程序运行起来之后，边跑边把字节码编译成本地机器码交给 CPU 执行。

解释执行是逐条读取字节码并实时翻译，每次运行都要重新翻译，CPython 默认就是这种模式。AOT 预先编译在运行之前一次性把源码编译成机器码，例如 C 语言经 gcc 编译后直接运行二进制。JIT 则在运行期监测高频执行的热点代码，把这一段动态编译成机器码缓存起来，后续调用直接执行机器码。

### 热点代码与动态优化

多数程序的大部分时间花在少量代码上。JIT 不会编译只执行一次的边角逻辑，而是在运行时采集统计信息，把循环和高频函数判定为热点后编译，并利用运行期信息做 AOT 难以完成的优化：

- 类型特化：发现某函数入参始终是 int，就生成专用机器码，省去动态类型检查。
- 去虚调用、函数内联、循环展开。
- 删除运行时确认永不进入的死分支。

### PyPy 的 JIT

PyPy 的核心卖点是 RPython JIT。反复执行的循环与函数会被编译成机器码，单线程性能常比 CPython 快数倍甚至数十倍。以一段一千万次累加的纯 Python 循环为例，CPython 全程解释执行，PyPy 跑几轮后识别循环为热点并编译，速度明显提升。

PyPy 有 JIT，但仍有 GIL。JIT 提升的是单条执行流跑代码的速度，不是多线程多核并行能力。

其他带 JIT 的运行时包括 Java HotSpot JVM 的 C1 与 C2 编译器、JavaScript 的 V8 引擎、GraalVM 的 Graal JIT，以及 .NET CLR。

### 优缺点

优点是热点代码大幅提速，动态语言收益尤其明显，且能利用运行时信息做针对性优化。

缺点是启动阶段尚未形成热点，只能解释执行，存在预热开销；需要额外内存存放机器码与 profiling 数据；编译本身消耗 CPU，短生命周期的一次性脚本可能还没等到 JIT 生效就结束，反而更慢。

### 常见混淆

- JIT 是运行期编译，AOT 是运行前编译。
- PyPy 等于 Python 实现加 JIT 编译器，但标准版仍带 GIL。
- CPython 原生不带 JIT，曾有的 Pyjion 项目基本搁置。
- JIT 与 GIL 是两件事：GIL 控制多线程能否同时执行字节码，JIT 控制单线程执行代码有多快。

## 用 multiprocessing 绕开 GIL

### 基本原理

multiprocessing 新建的是操作系统进程。每个子进程启动一份独立的 CPython 解释器，拥有自己的 GIL 与内存空间，操作系统可以把它们调度到不同 CPU 核上。父进程与各子进程各拿各的 GIL，互不干扰，从而实现真正并行。

代价是进程之间内存隔离，无法直接读写彼此的变量，通信开销明显高于线程。

完整链路可以概括为：父进程持有自己的 GIL，Process 创建子进程，子进程启动全新解释器并持有独立 GIL，操作系统把子进程放到另一个核上，两边同时推进。

### 创建进程与回收结果

Process 的 target 函数返回值无法由主线程直接读取，exitcode 只表示退出状态。需要用 Queue 或 Pipe 把结果传回来。

```python
import multiprocessing

def calc(start, end, q):
    s = 0
    for i in range(start, end):
        s += i
    q.put(s)

if __name__ == "__main__":
    q = multiprocessing.Queue()
    p1 = multiprocessing.Process(target=calc, args=(0, 5_000_000, q))
    p2 = multiprocessing.Process(target=calc, args=(5_000_000, 10_000_000, q))
    p1.start()
    p2.start()
    p1.join()
    p2.join()
    print(q.get() + q.get())
```

### 进程池

批量任务优先用 Pool，由它维护进程数量并自动分配任务，省去逐个 start 与 join。进程数一般设为 CPU 核心数，可用 multiprocessing.cpu_count 获取。

```python
import multiprocessing

def calc(start, end):
    s = 0
    for i in range(start, end):
        s += i
    return s

if __name__ == "__main__":
    args_list = [(0, 5_000_000), (5_000_000, 10_000_000)]
    with multiprocessing.Pool(processes=2) as pool:
        res = pool.starmap(calc, args_list)
    print(sum(res))
```

starmap 适合多参数函数，map 适合单参数函数，imap_unordered 在任务完成时就立刻返回，适合流式处理。

### 共享数据

默认情况下子进程拿到的是父进程数据的副本，在子进程里修改全局变量，父进程看不到。真正共享需要 Value、Array 或 Manager。

Value 与 Array 基于原生共享内存，速度最快，但只支持基础 C 类型，且必须自行加锁。下面的写法用跨进程锁修正了自增竞态，结果稳定为 2000。

```python
import multiprocessing

def add_one(v, lock):
    for _ in range(1000):
        with lock:
            v.value += 1

if __name__ == "__main__":
    shared_val = multiprocessing.Value('i', 0)
    lock = multiprocessing.Lock()
    p1 = multiprocessing.Process(target=add_one, args=(shared_val, lock))
    p2 = multiprocessing.Process(target=add_one, args=(shared_val, lock))
    p1.start()
    p2.start()
    p1.join()
    p2.join()
    print(shared_val.value)
```

Manager 可以共享 list 与 dict，能力更强，但底层经由管理服务进程与本地套接字转发，pickle 开销大，速度慢一些。multiprocessing.Lock 与 threading.Lock 用法相近，但作用范围不同，不能混用。

### 启动方式

- spawn：Windows 默认，安全但开销大，会重新导入主模块。
- fork：Linux 传统默认，复制父进程内存，速度快，但父进程持有锁或线程时，子进程状态容易异常。
- forkserver：由独立服务进程按需 fork，兼顾安全与开销。

可用 multiprocessing.set_start_method 显式指定。Windows 只能使用 spawn，此时必须把入口逻辑放在 if \_\_name\_\_ == "\_\_main\_\_" 之下，否则子进程重新导入模块会无限递归创建进程。Mac 与 Linux 也推荐保留这层保护。

### 常见陷阱

- 缺少主模块保护，在 spawn 模式下递归创建子进程。
- 直接修改全局变量，误以为父进程能看到子进程的改动。
- 任务粒度过小，进程创建与 IPC 开销超过计算收益，反而比串行更慢。进程适合粗粒度大任务。
- 混用 multiprocessing.Lock 与 threading.Lock。
- 每个进程都持有一份数据副本，进程数上去后内存成倍增长。

### 更高层封装

concurrent.futures.ProcessPoolExecutor 的 API 与 ThreadPoolExecutor 几乎一致，写起来更简洁，适合快速替换线程池做对比。

```python
from concurrent.futures import ProcessPoolExecutor

def calc(a, b):
    return a + b

if __name__ == "__main__":
    with ProcessPoolExecutor() as executor:
        res = executor.submit(calc, 1, 2)
        print(res.result())
```

### 适用边界

CPU 密集任务、矩阵运算、大量循环计算、模型推理，优先用多进程吃满多核。IO 密集任务优先用多线程或协程，进程太重，没有必要。

## Python 进程间通信

### 通信机制

multiprocessing 封装了多种底层 IPC，不是单一协议，不同 API 的底层并不相同。

Queue 与 SimpleQueue 基于操作系统匿名管道，附加内部锁保证线程安全，对象经 pickle 序列化后以字节流传输，适合生产者消费者模型。

Pipe 返回两个连接端，默认全双工，传入 duplex=False 时为单向。它同样基于匿名管道，对象经 pickle 序列化，比 Queue 轻量，没有额外锁，适合两个进程点对点通信。Pipe 只在本机使用，不跨机器。

Manager 会单独启动一个管理服务进程，各子进程通过本地套接字与它交互，读写共享的 list 与 dict。Unix 上是 AF_UNIX 域套接字，Windows 上是命名管道，都属于内核内通信，不走网卡，也不是 TCP/IP。

RawArray、Array 与 Value 基于操作系统共享内存段，直接在物理内存开辟所有进程都能访问的区域，没有数据拷贝，性能最优。代价是只能存放基础 C 类型，不能直接放 Python 对象，且需要手动加锁同步，适合图像、数值矩阵等大块数据。

此外还可自行使用命名管道 FIFO、System V 或 POSIX 消息队列、信号，以及跨主机的 TCP/UDP 套接字。

### 机制对比

| 工具 | 底层 IPC | 能否传 Python 对象 | 速度 |
| --- | --- | --- | --- |
| Pipe | 匿名管道 | 可以，经 pickle | 较快 |
| Queue | 管道加锁 | 可以，经 pickle | 中等 |
| Manager | UNIX 域套接字或 Windows 命名管道 | 可以，经 pickle | 慢 |
| Array 与 RawArray | 共享内存 | 不可以，仅基础 C 类型 | 最快 |

### IPC

IPC 指操作系统内核提供的本机通信机制，包括管道、共享内存、域套接字。

### 序列化限制

Queue、Pipe、Manager 传递 Python 自定义对象都要经过 pickle。打开的文件句柄、socket 连接等不可序列化对象无法直接传递。共享内存 Array 只能存简单 C 类型，不能直接放 Python 对象。

## C++ 进程通信

C++ 语言本身没有内置 IPC，工程上直接调用操作系统系统调用，或使用封装库屏蔽平台差异。Linux 与 Windows 各有一套常用机制，其原语也正是 Python multiprocessing 在底层的封装对象。

### Linux 机制

- 匿名管道 pipe：仅限有亲缘关系的进程，单向字节流，数据停在内核缓冲区。
- 命名管道 FIFO：以文件形式存在，任意进程可打开，仍是字节流。
- 管道类机制没有消息边界，传输业务数据需要自己分包。
- System V 消息队列：以 msgget、msgsnd 等接口操作，带消息类型，一条一条有边界。
- System V 共享内存：shmget 与 shmat，内存直接映射，无数据拷贝，是最快的 IPC，但本身不带同步，必须配合信号量。
- System V 信号量：semget，只做同步与互斥，不传业务数据。
- POSIX 消息队列 mq_open、POSIX 共享内存 shm_open、POSIX 信号量 sem_open，是现代推荐的一组接口，其中 shm_open 常用来替代 System V 共享内存。
- Unix Domain Socket，简称 UDS，使用 AF_UNIX 地址族，本质是 socket API 但在内核内通信，不走网卡，支持 SOCK_STREAM 字节流与 SOCK_DGRAM 数据报。它支持任意本机进程双向通信，还能传递文件描述符，这是它独有的能力，nginx、redis 等服务的内部多进程通信大量使用。
- 信号 signal：只能发送 SIGUSR1 这类简单通知，不能携带业务数据。

### Windows 机制

- 匿名管道与命名管道 Named Pipe，是 Windows 上大量程序使用的方案。
- 文件映射 File Mapping，对应 Linux 共享内存，配合 Mutex 与 Event 做同步。
- 邮槽 Mailslot，单向消息队列，支持广播。
- Windows 套接字在新版本中同样支持本地 UDS。

### 跨平台封装

- Boost.Interprocess：成熟稳定，封装共享内存、消息队列与命名管道，跨 Linux 与 Windows。
- absl 与 folly 中的 IPC 组件：多见于后端大厂工程。
- Qt 的 QSharedMemory 与 QLocalSocket，底层分别是共享内存和 UDS 或 Windows 命名管道。

### 机制对比

| IPC 类型 | 数据载体 | 是否拷贝 | 同步能力 | 适用场景 |
| --- | --- | --- | --- | --- |
| 管道与 FIFO | 字节流 | 拷贝 | 内核自带阻塞 | 简单单向数据流 |
| 共享内存 | 内存块 | 无拷贝 | 无，需要信号量或 mutex | 图像、点云等大数据高性能场景 |
| Unix Domain Socket | 字节流或数据报 | 拷贝 | 由流式语义保证 | 双向通信、传递 fd、服务内部 IPC |
| System V 与 POSIX 消息队列 | 消息单元 | 拷贝 | 按消息读写 | 固定长度任务队列 |
| 信号 | 仅信号编号 | 无 | 异步通知 | 简单事件触发，不传数据 |
